# ADR 0002 — Pure Swift, SPM core with an XcodeGen app target

- **Status:** Accepted
- **Date:** 2026-07-25
- **Deciders:** Project maintainer
- **Supersedes:** —

## Context

Aeolus needs, at minimum:

- IOKit access to the SMC
- A privileged launch daemon registered via `SMAppService`
- An `NSXPCConnection` boundary between unprivileged clients and that daemon
- A menu bar application and a main window
- A command-line client
- Universal binaries, hardened runtime, Developer ID signing, and notarisation

The privilege boundary is the deciding factor. It is the one part of the system where a
mistake is a security vulnerability in a root process, so the language and tooling choice
should be optimised for that seam being as boring and well-supported as possible.

## Decision

**Pure Swift 6 with strict concurrency**, built as a Swift Package Manager core plus an
Xcode app target whose project is generated by **XcodeGen**.

Supporting choices: swift-format and SwiftLint enforced in CI, Sparkle 2 for in-app
updates, swift-argument-parser for the CLI, and a macOS 13 deployment floor.

## Rationale

### Why Swift rather than a Rust or Go core

`SMAppService`, `NSXPCConnection`, IOKit, `MenuBarExtra`, notarisation, and universal
binaries are all first-class in Swift and all Apple-specific. There is no bridging
anywhere.

A Rust or Go core is defensible for the SMC layer alone — Rust calls IOKit perfectly well.
The problem is the privilege boundary: `NSXPCConnection` and `SMAppService` need
Objective-C bridging on **both** sides. That puts hand-written FFI in the most
security-critical seam of the project, written in the language with the least ecosystem
support for exactly that task, maintained by one person.

The general principle: the boundary between an unprivileged client and a root daemon is
the last place to introduce a language impedance mismatch.

### Why strict concurrency is non-negotiable

The helper is a long-lived actor-based service that samples sensors, evaluates curves,
supervises leases, and responds to power notifications concurrently. A data race there
does not produce a crash report — it produces a fan at the wrong speed, or a lease that
fails to expire. Swift 6's strict concurrency turns a class of hardware-safety bug into a
compile error, and that trade is worth the friction.

`@unchecked Sendable` is not an approved way out. It is a claim that the author has
verified something the compiler cannot, and in the helper that claim needs review.

### Why XcodeGen

`project.pbxproj` is effectively unmergeable. This project expects parallel work across
multiple branches, and every one of them would otherwise conflict in the same generated
file. `project.yml` is YAML: reviewable in a diff, mergeable, and it makes build
configuration an explicit artefact rather than something buried in Xcode's UI.

Tuist was the alternative — more capable, with real module graph management and caching.
Rejected as heavier than a six-target project needs. If the module count grows
substantially, revisiting is cheap: both tools consume a declarative spec.

### Why both a GUI and a CLI from day one

The tempting sequencing is CLI first, GUI later, because the CLI is easier and the early
audience is technical. But the stated goal is replacing a GUI application, and a CLI-first
project that never quite gets to the GUI is a common failure.

The architecture makes this a non-choice: the helper owns all state and all control, so
the app and the CLI are both thin clients of the same interface. Shipping both costs
little more than shipping either, and the CLI is genuinely the better tool for headless
Mac minis and SSH.

### Why macOS 13

`SMAppService.daemon(plistName:)` requires it. Newer affordances — some `MenuBarExtra`
behaviour in particular — are gated with availability checks rather than raising the floor,
because the Intel Macs most likely to need fan control are also the ones least likely to
be on the newest macOS.

## Alternatives considered

| Option | Verdict |
|---|---|
| **Swift + SwiftUI** | **Chosen.** Everything needed is first-class; zero bridging at the privilege boundary. |
| Rust or Go core with a Swift shell | Rejected. Puts FFI in the security-critical seam for no proportionate benefit. |
| CLI and daemon first, GUI later | Rejected as a sequencing decision. The architecture makes both cheap, and the stated goal is replacing a GUI app. |
| Electron or Tauri | Rejected. Cannot host a launchd daemon in-bundle cleanly, and is the wrong tool for a menu bar utility. |
| Committed `.xcodeproj` | Rejected. Unmergeable in a repository expecting parallel work. |
| Tuist instead of XcodeGen | Rejected as heavier than six targets justify. Revisit if the module graph grows. |

## Consequences

**Accepted cost: a narrower contributor pool.** Swift excludes people who would happily
contribute Go or Rust. This is real and it is mitigated rather than solved — by a
`Monitor` build that needs no certificate, small well-documented modules, a pure and fully
testable `FanKit`, and a sensor catalog contribution path that requires no Swift at all.

Further consequences:

- `Aeolus.xcodeproj` is generated and gitignored. Contributors run `xcodegen generate`,
  and `CONTRIBUTING.md` says so before anything else.
- Build configuration lives in `project.yml` and in `Package.swift`, in the repository,
  reviewable.
- The libraries, CLI, helper, and all tests build with plain `swift build` — no Xcode
  project needed for most work, and a fast CI loop.
- Sparkle's XPC services and the embedded helper make the signing order
  (inner-out) part of the release script rather than something done by hand.
- Mac App Store distribution is foreclosed, which the licence decision in
  [ADR 0001](0001-license.md) already implies and which the privileged helper independently
  requires.
