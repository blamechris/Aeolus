# Architecture

## Shape

```
┌──────────────────────┐        ┌──────────────────────┐
│  Aeolus.app          │        │  fanctl (CLI)        │
│  SwiftUI + MenuBar   │        │  argument-parser     │
└──────────┬───────────┘        └──────────┬───────────┘
           │        NSXPCConnection (mach service)      │
           └────────────────────┬──────────────────────┘
                                ▼
              ┌───────────────────────────────────┐
              │  AeolusHelper  (root launchd)     │
              │  ─ sole owner of all SMC writes   │
              │  ─ curve engine + control loop    │
              │  ─ safety supervisor + lease      │
              │  ─ client authorisation           │
              └────────────────┬──────────────────┘
                               │ IOKit
                    ┌──────────▼───────────┐
                    │  AppleSMC / IOHID    │
                    └──────────┬───────────┘
                               ▼
                        SMC firmware
```

Two clients, one privileged service. The GUI and the CLI are peers — neither is built on
the other, and both are thin.

## Targets

| Target | Kind | Responsibility |
|---|---|---|
| `SMCCore` | library | IOKit connection, key enumeration, type codec. Read API `public`; write API `@_spi(FanWrite) public`, nameable only from `AeolusHelper` ([ADR 0008 amendment](ADR/0008-write-authorisation.md)). |
| `FanKit` | library | Fan and sensor models, curve engine, profiles, config schema, sensor catalog. No IOKit. I/O limited to two named exceptions: reading the catalog file, and `sysctlbyname` for hardware identity (`hw.model`, `machdep.cpu.brand_string`) — never `uname -m`. |
| `AeolusXPC` | library | The `@objc` protocol and the Codable DTOs that cross the privilege boundary. |
| `AeolusHelper` | root daemon | The only writer. Listener, client authorisation, handshake gate, control loop, and safety supervisor. Internally split at the `FanAuthority` seam: everything from the mach port down to that protocol is E2's, everything behind it is E5's. |
| `fanctl` | executable | XPC client; also standalone in read-only mode. |
| `AeolusUI` | library | SwiftUI views and view models. |
| `Aeolus` | app bundle | Entry point, resources, embedded helper. Generated by XcodeGen. |
| `power-observer` | maintainer tool | Lives outside `Sources/`, at `Tools/PowerObserver`; not in `project.yml` and never shipped. A read-only `IORegisterForSystemPower` observer that logs every power notification IOKit delivers, unfiltered, for measuring [docs/SAFETY.md](SAFETY.md) row 14. Depends on nothing else in this package — only Foundation and IOKit — and never touches the SMC. See [Tools/PowerObserver/README.md](../Tools/PowerObserver/README.md). |

`FanKit` being pure is a deliberate constraint, not an accident of layering: the curve
engine, the clamping logic, and the lease arithmetic are exactly the things that must be
exhaustively testable without hardware.

## Why the control loop lives in the helper

The obvious design puts the curve engine in the app: it has the UI, it has the user's
settings, it knows what the user wants. It is the wrong place.

If the curve engine ran in the GUI, then quitting the app — or a GUI crash, or a hang, or
the user logging out — would leave the fans pinned at whatever value was last written,
with nothing left running to change them. The failure would be silent and it would persist
until reboot.

Putting the loop in the helper means the helper is always the authority on fan state, and
can enforce safety with no client present at all. The GUI becomes a view and an editor of
helper state. This is what makes "quitting always restores automatic control" a property
of the system rather than a promise the app tries to keep.

## The privilege boundary

`AeolusXPC` defines the entire contract. Everything on the far side runs as root.

**Client authorisation.** The helper checks each connecting process against a code-signing
requirement before honouring anything. Being able to connect to a mach service is not
authorisation; on a multi-user machine, any process can attempt it.

**Validation happens on the far side.** Fan speeds are clamped against firmware bounds
after they cross, not before they are sent. Client-side validation is a courtesy to the
user; helper-side validation is the actual control.

**Versioning.** `AeolusXPCVersion` is negotiated at connect and is independent of the
app's marketing version — a Homebrew-installed `fanctl` and a Sparkle-updated app will
routinely be at different releases. A client outside the supported range is rejected with
an explicit error. Silent degradation between a client and a root daemon is how safety
mechanisms end up not running.

**Wire format.** Structured payloads cross as JSON-encoded `Data` rather than as
`NSSecureCoding` class graphs. The result is a wire format that is versioned, loggable,
and reviewable, at the cost of some encoding overhead that does not matter at a 1 Hz
sample rate.

## Sensor and key model

### Key on the declared type, never on the architecture

The SMC encodes values differently on Apple Silicon and Intel:

| | Apple Silicon | Intel |
|---|---|---|
| Fan RPM | little-endian IEEE-754 (`flt`) | big-endian 14.2 fixed point (`fpe2`, i.e. RPM << 2) |
| Force manual | `F0Md` per-fan mode key (plus `Ftst` on M3+) | `FS!` bitmask, bit *n* = fan *n* |

It would be straightforward to branch on `uname -m`. It would also be wrong. The SMC
declares a type for every key, and reading that type gives one code path that is correct
on both generations and stands a chance of surviving future silicon. A single machine
also exposes keys of several types at once, so architecture is the wrong axis regardless.

`SMCKeyType` is that registry. An unrecognised type is preserved as `.unknown(FourCharCode)`
rather than discarded, so a Mac nobody has seen still shows every sensor it has.

#### Amendment (ADR 0003, widened by ADR 0004): the declared type determines format, not byte order

E1 found that "key on the declared type" was incomplete for one family of types, and
adversarial review before E4 found the incompleteness ran wider than first scoped. The
declared type still determines *format* unconditionally. But byte order is **not**
determined by the declared type alone for two groups:

- The plain integers (`ui16`, `si16`, `ui32`, `si32`, `ui64`, `si64`) — [ADR
  0003](ADR/0003-integer-byte-order.md).
- `flt` and `ioft` — [ADR 0004](ADR/0004-float-byte-order.md), which found ADR 0003's
  original "little-endian by construction" carve-out for these two types unsupported by
  the evidence and contradicted by Asahi's own documentation of a byte-reversed `flt` key.

For both groups, byte order is firmware-declared per key: attribute bit `0x04` on the
modern (Apple Silicon) interface (set → little-endian, clear → big-endian), and fixed
unconditionally by type on the legacy (Intel) interface — big-endian for the plain
integers, little-endian for `flt`/`ioft`, with the attribute byte never consulted there
(VirtualSMC documents that bit as `ATTR_ATOMIC` on Intel, an unrelated meaning).
`fpe2`/`fp78`/`sp78` remain big-endian by definition of the type, unconditionally, on both
generations — genuinely fixed, not firmware-declared; ADR 0004 declined to extend the
per-key rule to them since they have zero occurrences on `.modern` and no source describes
their behaviour there. See `resolveByteOrder(generation:attributes:type:)` in
`Sources/SMCCore/SMCByteOrderResolver.swift` for the evidence and the single function that
owns the rule for all of it.

This still bans `uname -m` — it does not weaken the ban, it gives it a sharper
justification. The generation half of the resolved metadata is read once per connection
from the `AppleSMC` IOService's own IORegistry provenance (`SMCConnection.open()`), never
from the process's architecture, which reports the wrong thing entirely (the running
process, not the firmware) and lies outright under Rosetta.

**No control-path key's byte order is unambiguously fixed by its type on this machine.**
Fan RPM on Apple Silicon (`F0Ac`, `F0Mn`, `F0Mx`, `F0Tg`) is `flt`; temperatures are
`flt`/`ioft`/`sp78`; Intel fan RPM is `fpe2`. Every readable `flt` key (2073 of them) and
`ioft` key (10 of 11 readable) on `Mac16,5` carries attribute bit `0x04` set, and every
control-path fan key individually so — `F0Ac`/`F1Ac` (132), `F0Mn`/`F1Mn` (132),
`F0Mx`/`F1Mx` (133), `F0Tg`/`F1Tg` (212) — so routing them through the resolver is a
**provable no-op** on this machine: decoded output is byte-identical to the prior
unconditional rule. Mode keys (`F0Md`, `Ftst`, `FNum`) are single-byte `ui8`, which has no
byte order to resolve; Intel's `FS!` bitmask is `ui16` but exists only on the legacy
interface, where big-endian is unconditional regardless of the resolver.

Nothing on `Mac16,5` can establish whether the attribute bit is the *reason* `flt`/`ioft`
decode correctly here, as opposed to byte order simply being a fixed property of those
types that happens to agree with the bit on every key this hardware can read: every
readable `flt`/`ioft` key on this machine carries the bit set, so there is no readable
bit-clear key to discriminate the two hypotheses. ADR 0004 folds `flt`/`ioft` into the
per-key rule anyway, because the failure modes are asymmetric, not because the ambiguity
was resolved by measurement — see that ADR's Rationale. Whether the bit governs `flt` on
other firmware remains open; the designated discriminator is an M1/M2 report of `VP3b`'s
type, attributes, and raw bytes.

If the interface generation cannot be determined for a connection, every key whose byte
order is firmware-declared per key — the plain integers and, since ADR 0004, `flt`/`ioft`
— surfaces raw bytes only: `SMCValue.scalar()` returns `nil` rather than decoding with a
guessed order, and logs. Refusing to guess beats guessing; this now covers the control
path, not just display-grade integers. `#KEY` is the one exception, and by necessity:
without a key count nothing can be enumerated, control path included, so
`SMCConnection.keyCount()` decodes it directly as big-endian in the enumeration layer
instead — a guess, not a resolved fact, validated on every connection by
`verifyKeyCountCrossCheck()`'s independent walk of the table. See
`SMCConnection.decodeKeyCountFallback(value:)`.

### Discovery is dynamic

Key enumeration walks `#KEY` and the index table. There is no hard-coded key list, because
a hard-coded list silently omits sensors on every Mac the authors have not personally
owned — and that is nearly all of them.

The named constants in `SMCKey` exist because the control path needs certain keys by name.
They are not an inventory.

### The catalog only decorates

`Resources/catalog/catalog.json` maps raw keys to human-readable labels, scoped by chip
family and model. It is shipped as a bundle resource and hot-loadable from
`~/Library/Application Support/Aeolus/catalog.json`.

Three properties follow from it being decoration rather than data:

1. A machine with no matching catalog entries works completely, showing raw keys.
2. The raw key is always displayed alongside any label. A wrong label must never be able
   to quietly mislead someone into driving a fan from the wrong sensor.
3. Every label carries a confidence level, shown in the UI. A guess is displayed as a
   guess.

### Two possible sensor providers

Some Apple Silicon thermal sensors are exposed through `IOHIDEventSystemClient` rather
than the SMC — this is what `powermetrics` reads. Whether Aeolus needs both providers or
the SMC alone suffices is **an open question**, and E1 is expected to answer it from
observed behaviour rather than from community summaries.

`SensorProvider` exists so that either answer is absorbed without churn above it.

## The Apple Silicon write path

On Intel and on M1/M2, requesting manual fan control is a straightforward SMC write. From
M3 onward it is not: `thermalmonitord` holds the fans and the firmware rejects the naive
mode write with error `0x82`.

The sequence that reportedly works:

1. Write the mode key (`F0Md = 1`) directly. Succeeds on M1/M2, and on M3+ when the
   system is not actively asserting control.
2. On rejection, write the diagnostic force key `Ftst = 1`.
3. Wait for the thermal manager to yield — poll, do not sleep blindly.
4. Retry the mode write with a bounded retry budget.
5. Write the target RPM.
6. On release, restore automatic mode **and** clear `Ftst`.

The critical follow-on: **sleep and wake reset `Ftst` in firmware**, and the system takes
the fans back. That is not a licence for the helper to re-assert on wake:
[ADR 0007](ADR/0007-safety-composition.md) rules that it must not, because an unbidden write
racing the firmware for control the helper has just released is the "claims control it does
not have" failure wearing a fix's clothes.

What the helper owes here is detection and honesty. The reclamation watchdog notices, the
snapshot reports it, and a client that still wants the fans re-acquires deliberately —
re-running the unlock through the ordinary grant path. Without that, manual control silently
stops working the first time the lid closes while the UI carries on showing a target speed
nothing is honouring, which is the same failure by a different route. See
[SAFETY.md](SAFETY.md) § 4 and § 5.

This is the highest-risk area of the project. It is treated as a research task with a
written findings document (`SMC-RESEARCH.md`), not as a coding task, and the numbers above
are community reports rather than anything verified here.

## Build configurations

`Monitor` builds everything except the write path: no helper, no entitlements, ad-hoc
signable. `Full` embeds and registers the privileged helper and requires a Developer ID.

`Full` puts the helper at `Contents/MacOS/AeolusHelper` and its launchd job description at
`Contents/Library/LaunchDaemons/com.blamechris.Aeolus.Helper.plist`, and registers it with
`SMAppService.daemon(plistName:)`. The job description names the helper by a
**bundle-relative** `BundleProgram`, never an absolute path, which is what makes deleting
the app equivalent to removing the daemon.

`Monitor` contains neither file. The app decides what it may do about a helper by
**looking in its own bundle at runtime** rather than by consulting a compile-time flag —
see `HelperBundleLayout`. A build with no helper in it never asks `SMAppService` anything,
and says "no privileged helper in this build" rather than "the helper is not running",
which would imply one exists.

CI builds `Monitor` on every pull request. It cannot do more — GitHub's macOS runners are
virtual machines with no SMC, so they can build, lint, test, sign, and notarise, but they
cannot validate that a single fan write does what it claims. Hardware verification is
manual and always will be.
