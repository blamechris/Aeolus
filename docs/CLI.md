# fanctl

`fanctl` is Aeolus's command-line client. Its read commands — `list`, `sensors`, `watch`,
`dump` — talk directly to the SMC through `SMCCore`/`FanKit`, exactly as the app's own
read path does, and need no installed helper, no signing, and no privileges at all. This
is what makes them usable from a headless Mac mini over SSH, and why
[`hardware-report.yml`](../.github/ISSUE_TEMPLATE/hardware-report.yml) and
[`sensor-catalog.yml`](../.github/ISSUE_TEMPLATE/sensor-catalog.yml) both ask contributors
to paste their `--json` output directly: nothing about producing it depends on Aeolus.app
being installed, or on the machine having ever run it.

Write commands (`fanctl reset`, and fan control once E10b lands) are a different story —
a thin shell over the same XPC calls the GUI makes, gated by the same lease and the same
client-authorisation check. This document is about the read commands' `--json` output
only.

## `--version`

Reports two independent numbers: `fanctl`'s own release version, and
`AeolusXPCVersion.current` — the XPC wire protocol version *this build supports*, read as
the plain constant it is declared as in `Sources/AeolusXPC/AeolusXPCProtocol.swift`.
**This never opens a connection or negotiates with a running helper** — none of `fanctl`'s
read commands do — so it is phrased as "supports," not "speaks to" or "connected to."
A Homebrew-installed `fanctl` and a Sparkle-updated `Aeolus.app`/helper routinely disagree
on the tool version without disagreeing on the protocol version; that is why the two are
reported separately rather than folded into one number.

## Shell completions

`fanctl --generate-completion-script <bash|zsh|fish>` prints a completion script for the
named shell, generated by `swift-argument-parser` from the command tree itself — there is
nothing to hand-maintain, and no completion script is checked into this repository. See
each shell's own documentation for where to install the output (typically a file under
`/usr/local/etc/bash_completion.d`, `~/.zsh/completions`, or `~/.config/fish/completions`).
`Tests/fanctlTests/FanctlCommandTests.swift` asserts a script is generated for every
supported shell and names every subcommand, so a renamed or dropped subcommand fails a
fast unit test rather than silently going stale in a user's shell profile.

## Error format

`list`, `sensors`, `watch`, and `dump` all raise one shared type, `FanctlError`
(`Sources/fanctl/FanctlError.swift`), for every runtime failure — no SMC found, a read
that should have succeeded failing anyway, an implausible decoded value, a `--json`
encoding failure, or (for `dump --key`) a well-formed key this machine's table does not
contain. A malformed *argument* (`--key` of the wrong length, a non-positive `--interval`
or `--count`) is a different category of problem — how the command was invoked, not what
happened once it ran — and is rejected before any hardware I/O as a `ValidationError`
instead, with its own usage block. Neither path ever prints a bare `nil`, an `SMCError`
case name, or a stack trace.

## `--json`: general conventions

- **`list`, `sensors`, and `dump`** pretty-print with sorted keys (`FanctlJSON.encode`),
  since `hardware-report.yml`/`sensor-catalog.yml` ask a human to paste the result
  straight into a GitHub issue body before anything parses it.
- **`watch --json`** is newline-delimited JSON (NDJSON) instead: one *compact*, sorted-key
  object per refresh, with no embedded newline, so `jq -c` or a shell's `while read -r
  line` can consume it as a stream. It never carries ANSI escapes, on a terminal or not.
- Dates are ISO 8601 (`capturedAt` on `list`/`sensors`/`watch`).
- A field that is a **named part of one entry** (a per-fan `KeyedValue` on `list`, a
  per-sensor `SensorJSON` on `sensors`) is always present, `null` standing in for "not
  available" — this is a hand-written `Encodable` conformance specifically so the field
  set never changes shape between entries. A field that is **document-level, optional
  context** (`sensors`' top-level `keysDeclared`/`keysSkipped`, `dump`'s top-level
  `crossCheck`, and every optional field on a `dump` row) is **omitted entirely**, not
  encoded as `null`, when unavailable — the default `Codable` synthesis for `Optional`
  properties. Both conventions are intentional and stable; they are just not the same
  convention, and this is the one place that says so.
- A non-finite reading (`NaN`/`±Infinity` — a byte-order fault, not real hardware; see
  `docs/SMC-RESEARCH.md`) is sanitised to `null` plus a string `error` *before* it can
  reach the encoder, never left to make `JSONEncoder` throw and void the entire document
  for one bad key among however many others read cleanly.

<a id="fanctl-list-json"></a>

## `fanctl list --json`

Every fan's current, minimum, and maximum RPM, keyed by the raw SMC key that produced
each value — never hidden behind the synthesised `displayName`.

```json
{
  "capturedAt": "2025-01-01T00:00:00Z",
  "fanCount": { "key": "FNum", "value": 2 },
  "fans": [
    {
      "index": 0,
      "displayName": "Fan 0",
      "actualRPM": { "key": "F0Ac", "value": 1712, "error": null },
      "minimumRPM": { "key": "F0Mn", "value": 1200, "error": null },
      "maximumRPM": { "key": "F0Mx", "value": 5312, "error": null }
    }
  ]
}
```

`value`/`error` on a `KeyedValue` are mutually exclusive — a failed read is `value: null`
plus a specific `error` string, never a fabricated `0`. `fanCount.value` can legitimately
be `0` (a fanless Mac; `FNum` genuinely absent is treated the same as `FNum == 0`, per
community reports of some fanless Apple Silicon Macs) — that is a fact about the hardware,
not an error, and `fans` is simply empty in that case.

<a id="fanctl-sensors-json"></a>

## `fanctl sensors --json`

Every sensor this machine's SMC exposes, decorated with a catalog label where one is
known. This is the payload `sensor-catalog.yml` and `hardware-report.yml` both ask for.

```json
{
  "provider": "smc",
  "capturedAt": "2025-01-01T00:00:00Z",
  "sensorCount": 2929,
  "keysDeclared": 3385,
  "keysSkipped": 456,
  "sensors": [
    {
      "key": "Tp09",
      "label": "CPU Efficiency Cluster",
      "category": "cpu",
      "labelConfidence": "community",
      "value": 42.5,
      "error": null,
      "unit": "celsius"
    },
    {
      "key": "F0Ac",
      "label": null,
      "category": null,
      "labelConfidence": null,
      "value": 1712,
      "error": null,
      "unit": "rpm"
    }
  ]
}
```

- `key` is always present, on every entry, unconditionally — this is `docs/SAFETY.md`'s
  "always show the raw SMC key alongside any friendly label" rule made concrete in the
  wire format itself, not just in the table view.
- `label`/`category`/`labelConfidence` are `nil` together, never one without the others —
  an unlabelled sensor (no catalog wired in, or no catalog entry matches this machine) is
  a normal result, not a degraded one. `--raw-keys` forces all three to `null` even where
  a catalog match exists, and never touches `key`.
- `category` is one of `cpu`, `gpu`, `memory`, `storage`, `battery`, `power`, `ambient`,
  `display`, `fan`, `other`. Added in #60, after `sensors --json` first shipped in #51 —
  a raw catalog match always carries one, so it is `nil` exactly when `label`/
  `labelConfidence` are, never independently.
- `labelConfidence` is `verified`, `community`, or `guess` — never hidden behind a
  friendlier label. A guess is shown as a guess.
- `keysDeclared` (`#KEY`'s own declared value, read independently of the full
  enumeration) and `keysSkipped` (`keysDeclared` minus `sensorCount` — keys `readAll()`
  silently could not decode at any stage) are **omitted from the document entirely**,
  not `null`, on a machine or connection where `#KEY` itself could not be read — this is
  diagnostic context for a hardware report, never something `sensors`' success depends
  on.
- `unit` is one of `celsius`, `rpm`, `watts`, `volts`, `amps`, `percent`, `unknown`.

<a id="fanctl-watch-json"></a>

## `fanctl watch --json`

One compact NDJSON line per refresh tick, in **exactly** `list --json`'s field shape —
`capturedAt`/`fanCount`/`fans`, same names, same nesting — because `watch` fetches through
`ListCommand.fetch` and renders through `ListCommand.jsonOutput` directly. `watch` can
never show a different number than `list` for the same key by construction, not by
discipline. The only difference is framing: compact rather than pretty-printed, one
self-contained value per line, never spanning a newline.

```
{"capturedAt":"2025-01-01T00:00:00Z","fanCount":{"key":"FNum","value":2},"fans":[...]}
{"capturedAt":"2025-01-01T00:00:01Z","fanCount":{"key":"FNum","value":2},"fans":[...]}
```

<a id="fanctl-dump-json"></a>

## `fanctl dump --json`

A full SMC key-table enumeration for hardware reports and ADR research — a research and
diagnostic tool for contributors, distinct in purpose from `list`/`sensors`/`watch`'s
end-user monitoring. `--key <KEY>` (exactly four characters, e.g. `VP3b`) filters down to
one row, which is the pasteable form `hardware-report.yml`'s byte-order-discriminator
field asks for; the unfiltered dump is hundreds of kilobytes on `Mac16,5` alone, well past
what a GitHub issue body accepts.

```json
{
  "generation": "modern",
  "declaredKeyCount": 3385,
  "crossCheck": {
    "matches": true,
    "declaredCount": 3385,
    "walkedCount": 3385,
    "keyExistsPastDeclaredCount": false
  },
  "entries": [
    {
      "index": 1675,
      "key": "VP3b",
      "type": "flt ",
      "dataSize": 4,
      "attributes": 133,
      "byteOrder": "little-endian",
      "bytes": "8020e73f"
    }
  ]
}
```

- `generation` is `modern` (Apple Silicon), `legacy` (Intel), or `undetermined`.
- `crossCheck` is **omitted from the document entirely**, not `null`, when
  `SMCConnection.verifyKeyCountCrossCheck()` itself could not run — it independently
  re-probes index `declaredCount` (which the main walk never visits) to catch `#KEY`
  under-declaring the real table; `matches: false` plus `keyExistsPastDeclaredCount: true`
  is the signal that happened.
- Every field on an entry past `index`/`key` is **omitted from that entry entirely**, not
  `null`, whenever it is unavailable — `type`/`dataSize`/`attributes`/`byteOrder`/`bytes`
  can each be missing depending on which of `docs/SMC-RESEARCH.md`'s three read-failure
  modes (if any) this key hit; `error` is omitted only on a full success. `bytes` is the
  empty string `""` (present, not omitted) for a zero-length successful read — an empty
  payload is still a successful one. `byteOrder` is omitted whenever nothing in
  `SMCValue.scalar()`'s decode path ever actually consults a resolved order for that type
  (`fpe2`/`fp78`/`sp78`, single-byte types, `{fds`/`{jst`/`ch8*`/`hex_`/unknown) — showing
  a number there would be arithmetically computable but evidentially false, since nothing
  downstream reads it.
- `--key` matching nothing among `declaredCount` keys is a runtime `FanctlError` (a fact
  about this machine's key table), not a `ValidationError`; `--key` of the wrong length is
  a `ValidationError`, rejected before any hardware I/O — see "Error format" above.

## Keeping this document honest

This document is generated by reading `Sources/fanctl/ListCommand.swift`,
`SensorsCommand.swift`, `WatchCommand.swift`, and `DumpCommand.swift` directly, not by
assumption. If a `--json` shape changes, update this file in the same pull request —
`hardware-report.yml` and `sensor-catalog.yml` both depend on the exact invocations named
here continuing to produce what this document describes.
