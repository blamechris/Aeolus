# `fanctl` — command reference and `--json` shapes

`fanctl` is the CLI client: `list`, `sensors`, `watch`, and `dump` read directly through
`SMCCore`, never over XPC, so all four work standalone — no helper installed, no signing,
no privileges. This is the durable reference for what they print, in both human and
`--json` form, and it is the document `.github/ISSUE_TEMPLATE/hardware-report.yml` and
`.github/ISSUE_TEMPLATE/sensor-catalog.yml` point at: both ask contributors to paste
specific `--json` invocations directly into an issue body, and this is where that shape
is defined and kept stable.

`status`, `set` and `auto` talk to the helper instead; they and the exit codes every helper
command shares are in [Commands that talk to the helper](#commands-that-talk-to-the-helper).

Every example below is real output, captured by actually running the command — not
hand-written. Where a shape genuinely changed recently (`sensors --json` gained
`category`, `dump --json` gained `crossCheck` and `--key`, `watch --json` moved to
NDJSON), this document describes what is on `main` today, not what an earlier PR shipped.

---

## `--version`

```
$ fanctl --version
fanctl 0.0.0-dev
XPC protocol 2 (protocol version this build supports; not a negotiated connection —
see docs/ADR/0005-xpc-authorisation.md for the helper's own connect-time handshake)
```

Two independent numbers, deliberately never conflated into one:

- **`fanctl <version>`** — this build's own tool version. Bumped by hand alongside a
  release; unrelated to the XPC protocol number.
- **`XPC protocol <N>`** — `AeolusXPCVersion.current`, a public compile-time constant
  this binary links against (`Sources/AeolusXPC/AeolusXPCProtocol.swift`). Reading it
  costs nothing and touches no helper: `fanctl`'s read commands never open an XPC
  connection at all, and `--version` itself connects to nothing either.

**Read this as "the protocol version this build supports," never as "the protocol
version negotiated with an installed helper."** Those are genuinely different claims.
[ADR 0005](ADR/0005-xpc-authorisation.md) makes the helper *enforce* version negotiation
at a `hello` handshake — a client outside `[minimumSupported, current]` is refused, with
both sides' ranges in the refusal. `--version` cannot know what any installed helper
actually accepts; only a real connection attempt can prove that. `fanctl status` is that
connection attempt: it completes a `hello` and prints the version it *negotiated*, labelled
as such, beside the one this build speaks — see [below](#fanctl-status).

## Shell completions

Generated by swift-argument-parser from `fanctl`'s own command tree
(`--generate-completion-script`), and committed under `Resources/completions/` —
`fanctl.bash`, `fanctl.zsh`, `fanctl.fish` — rather than generated at install time, so a
`from-source` or Homebrew build has them for free with no extra build step.

Regenerate after any change to a subcommand, option, or flag under `Sources/fanctl/`:

```
scripts/generate-completions.sh
```

Manual installation (until a Homebrew formula does this automatically):

```sh
# bash — requires bash-completion
fanctl --generate-completion-script bash > /usr/local/etc/bash_completion.d/fanctl

# zsh — anywhere on $fpath, e.g.:
fanctl --generate-completion-script zsh > /usr/local/share/zsh/site-functions/_fanctl

# fish
fanctl --generate-completion-script fish > ~/.config/fish/completions/fanctl.fish
```

## Errors: the contract every command follows

One shared type, `FanctlError` (`Sources/fanctl/FanctlError.swift`), formats every
runtime failure across all four read commands — `list`, `sensors`, and `dump` throw it
directly; `watch` throws it too, since it is built on `ListCommand.fetch` rather than a
parallel implementation. There is exactly one place that decides what "actionable" means
for this CLI, so the same underlying failure (no SMC, a connection that will not open, an
implausible decoded value) reads the same way regardless of which command hit it.

| | Usage mistake (`ValidationError`) | Runtime failure (`FanctlError`) |
|---|---|---|
| Example | `fanctl watch --interval 0`, `fanctl dump --key toolong` | No SMC on this machine, a dead connection, `#KEY` unreadable |
| Exit code | 64 (`EX_USAGE`) | 1 |
| Output | The message, plus a usage/help block | Only the message — no usage block |
| Meaning | "You typed something wrong" | "Something about this machine or its firmware went wrong" |

A usage block under a runtime failure would wrongly imply the user mistyped the command,
which is why `FanctlError` conforms to `LocalizedError` rather than being thrown as
`ValidationError` — see that type's own documentation. Every case renders a specific
message: never a bare `nil`, never a raw `SMCError`/`SensorReadFailure` case name, never
an unhandled stack trace.

Real examples, captured on `Mac16,5`:

```
$ fanctl dump --key toolongkey
Error: --key must be exactly four ASCII characters (e.g. VP3b); got 'toolongkey' (10 characters).
Usage: fanctl <subcommand>
  See 'fanctl --help' for more information.
$ echo $?
64
```

```
$ fanctl dump --key ZZZZ
Error: No key 'ZZZZ' found among the 3385 keys this machine's index table exposes.
$ echo $?
1
```

The second is a fact about the hardware, discovered only after a full index walk — not a
usage mistake — so there is no usage block, and the exit code is a plain `1`.

**Non-finite values never reach `--json`.** `SMCValue.scalar()` applies no finiteness
guard on the way out of `SMCCore`, so a byte-order fault can in principle decode to
`NaN`/`±Infinity`. `list` and `sensors` both sanitise every reading before it reaches
either renderer: a non-finite value becomes `"value": null` plus a specific `"error"`
string, the same shape a genuinely failed read already produces — never a fabricated `0`,
and never something that would make `JSONEncoder`'s default
`nonConformingFloatEncodingStrategy` throw and void the entire document.

## `--json` shapes

All four commands' `--json` output goes through `FanctlJSON` (`Sources/fanctl/
FanctlJSON.swift`): ISO 8601 dates, and — with the one deliberate exception of `watch`,
described below — pretty-printed with sorted keys, so a human can skim a pasted dump in a
GitHub issue before any script parses it.

### `fanctl list --json`

```json
{
  "capturedAt" : "2026-07-31T01:54:05Z",
  "fanCount" : {
    "key" : "FNum",
    "value" : 2
  },
  "fans" : [
    {
      "actualRPM" : {
        "error" : null,
        "key" : "F0Ac",
        "value" : 1351.9857177734375
      },
      "displayName" : "Fan 0",
      "index" : 0,
      "maximumRPM" : {
        "error" : null,
        "key" : "F0Mx",
        "value" : 5777
      },
      "minimumRPM" : {
        "error" : null,
        "key" : "F0Mn",
        "value" : 1350
      }
    }
  ]
}
```

- **`fanCount`** — `{ "key": "FNum", "value": <Int> }`. `key` is always `"FNum"` today;
  carried as an object rather than a bare number so a future fan-count source does not
  need a shape change.
- **`fans[].displayName`** — `"Fan <index>"`, synthesised by this CLI for a human to
  read. **Never** presented as something the firmware reported — Apple Silicon has no
  `{fds` fan-descriptor key, so there is no firmware name to show. The raw key is always
  present alongside it (see below), never replaced by it.
- **`actualRPM` / `minimumRPM` / `maximumRPM`** — the `KeyedValue` shape, identical across
  all three fields and reused by `sensors`' per-sensor `value`/`error` pair:
  `{ "key": String, "value": Double?, "error": String? }`. `value` is `nil` exactly when
  `error` is non-`nil` — a failed or non-finite read is recorded, never fabricated as `0`
  and never silently omitted. `key` is always present, so a wrong or missing reading can
  never be mistaken for a different sensor than the one it actually came from.

A fanless Mac (`FNum` absent or `0`) still produces valid, well-formed JSON:
`"fans": []`.

### `fanctl sensors --json`

```json
{
  "capturedAt" : "2026-07-31T02:04:13Z",
  "keysDeclared" : 3385,
  "keysSkipped" : 456,
  "provider" : "smc",
  "sensorCount" : 2929,
  "sensors" : [
    {
      "category" : null,
      "error" : null,
      "key" : "#KEY",
      "label" : null,
      "labelConfidence" : null,
      "unit" : "unknown",
      "value" : 3385
    },
    {
      "category" : "cpu",
      "error" : null,
      "key" : "Tp09",
      "label" : "CPU Efficiency Core Cluster",
      "labelConfidence" : "community",
      "unit" : "celsius",
      "value" : 42.5
    }
  ]
}
```

- **`sensorCount`** — how many keys decoded to a usable numeric scalar, i.e.
  `sensors.count`. **Not** the same as `keysDeclared`: `readAll()` silently skips any key
  that fails index lookup, `READ_KEYINFO`, `READ_BYTES`, or scalar decoding at any stage.
- **`keysDeclared`** — `#KEY`'s own declared value, read as an independent, dedicated
  subset read rather than assumed present among `sensors` — `null` if that one extra read
  itself did not succeed. Diagnostic context only; never something `sensors`' own success
  depends on.
- **`keysSkipped`** — `keysDeclared - sensorCount` when `keysDeclared` is known, `null`
  otherwise. Made explicit rather than left for a reader to notice the gap between two
  numbers in two different places — on `Mac16,5` at the time of writing, `keysDeclared`
  is `3385` and `sensorCount` is `2929`: 456 keys silently dropped by `readAll()`.
- **`sensors[].category`** / **`label`** / **`labelConfidence`** — `null` together, never
  one without the others: an unlabelled sensor (no catalog wired in, or `--raw-keys`, or
  simply no matching entry) is a normal result, not a degraded one. `category` is one of
  `cpu`, `gpu`, `memory`, `storage`, `battery`, `power`, `ambient`, `display`, `fan`,
  `other`; `labelConfidence` is one of `verified`, `community`, `guess` — see
  [CATALOG.md](CATALOG.md) for what each confidence level actually means.
- **`sensors[].key`** — always present, regardless of `--raw-keys` or a catalog match.
  Per this project's labelling rule (`docs/SAFETY.md`): a label is decoration, the raw
  key is the fact, and the two are never shown one without the other.
- **`sensors[].unit`** — one of `celsius`, `rpm`, `watts`, `volts`, `amps`, `percent`,
  `unknown`.

`--raw-keys` suppresses only the label lookup (`category`/`label`/`labelConfidence` all
`null`) — it never hides `key`, `value`, or `error`.

### `fanctl watch --json`

NDJSON: **one compact JSON object per line, line-buffered**, on a terminal or piped —
never pretty-printed, and never carrying the redrawing table's ANSI escapes. This is the
one command whose `--json` deliberately does not go through `FanctlJSON.encode(_:)`'s
usual pretty-printing (see `FanctlJSON.encodeLine(_:)`): `watch` is a long-running stream
a script tails line by line, where a multi-line object per tick would make "one JSON
value per line" — NDJSON's entire contract, and what makes `jq -c` or
`while read -r line` work — impossible to tell apart from the next tick's.

```json
{"capturedAt":"2026-07-31T01:54:42Z","fanCount":{"key":"FNum","value":2},"fans":[{"actualRPM":{"error":null,"key":"F0Ac","value":1362.6917724609375},"displayName":"Fan 0","index":0,"maximumRPM":{"error":null,"key":"F0Mx","value":5777},"minimumRPM":{"error":null,"key":"F0Mn","value":1350}},{"actualRPM":{"error":null,"key":"F1Ac","value":1454.96875},"displayName":"Fan 1","index":1,"maximumRPM":{"error":null,"key":"F1Mx","value":5777},"minimumRPM":{"error":null,"key":"F1Mn","value":1350}}]}
```

Each line is exactly `list --json`'s field shape (same `fanCount`/`fans`/`KeyedValue`
structure, same `capturedAt` per tick) — `watch` builds every tick from
`ListCommand.jsonOutput(_:)`, the same function `list` itself calls, so the two can never
drift into describing the same reading differently.

### `fanctl dump --json`

The research/diagnostic command behind [ADR 0004](ADR/0004-float-byte-order.md); not
part of the two issue templates above, but documented here for the same reason: its
shape moved recently (a `crossCheck` envelope, and `--key` to scope one row).

```json
{
  "crossCheck" : {
    "declaredCount" : 3385,
    "keyExistsPastDeclaredCount" : false,
    "matches" : true,
    "walkedCount" : 3385
  },
  "declaredKeyCount" : 3385,
  "entries" : [
    {
      "attributes" : 133,
      "byteOrder" : "little-endian",
      "bytes" : "8080e63f",
      "dataSize" : 4,
      "index" : 1675,
      "key" : "VP3b",
      "type" : "flt "
    }
  ],
  "generation" : "modern"
}
```

- **`generation`** — `"modern"`, `"legacy"`, or `"undetermined"`.
- **`crossCheck`** — `null` if it could not be computed; otherwise a re-probe of index
  `declaredKeyCount` itself (never visited by the ordinary walk), catching a `#KEY` that
  under-declares the real key table. See `KeyCountCrossCheck` and
  `SMCConnection.verifyKeyCountCrossCheck()`. `walkedCount` counts every index the firmware
  answered with a key code, including a nonzero one `SMCKey` refuses, while the walk found at
  least one key and there are at most eight of those (#623); `KeyTableWalk.walkedCount` states
  the rule. Such an index still has its own `entries[]` row, with the error.
- **`entries[]`** — one row per walked index, `DumpEntry`. Unlike `list`/`sensors`'
  hand-written `Encodable` conformances, `DumpEntry` uses the compiler-synthesised one:
  a `nil` field (e.g. `error` on a fully successful row) is **omitted from the JSON
  entirely**, not emitted as an explicit `null`. This is the one place in this CLI's
  `--json` output where a field's absence, rather than an explicit `null`, is the
  documented "not applicable" signal — a deliberate difference from `list`/`sensors`
  worth knowing before writing a parser against both.
- **`--key VP3b`** filters `entries` to the matching row(s) — the pasteable form for a
  hardware report; the unfiltered dump is hundreds of kilobytes as `--json`, well past
  what a GitHub issue body accepts.

## Commands that talk to the helper

`status`, `set` and `auto` need the helper installed, approved in System Settings, and willing to
accept this binary's signature. A `fanctl` built with `swift build` carries no Team ID and is refused at
both ends by design (ADR 0005), so it cannot reach an installed helper; the read commands
above need none of this and keep working.

The binary the helper is built to admit is the copy inside the app, `Aeolus.app/Contents/MacOS/fanctl`.
It is built from the same `Sources/fanctl` by the `fanctl` target in `project.yml`, which signs it with
the code-signing identifier `com.blamechris.fanctl` — the one name the helper's client requirement
allow-lists besides the app's. That identifier is declared once, in the target's
`PRODUCT_BUNDLE_IDENTIFIER`, and `CommandLineIdentifierDriftTests` holds it equal to the constant the
requirement is built from. On 2026-10-09, on `Mac16,5` / macOS 27.0.1, an installed Developer ID
`Full Release` helper admitted the Developer ID–signed copy (`fanctl status`, exit 0) and refused two
Developer ID–signed probes that each failed one clause of its requirement. An ad-hoc `swift build`
copy never reaches the helper at all: it carries no Team ID, so it refuses to connect and exits 3
([the hardware check on #82](https://github.com/blamechris/Aeolus/issues/82#issuecomment-6076882014)).

**The examples in this section are not captured from an installed helper.** The 2026-10-09 check
above reached one, but its output was summarised in that issue and not recorded verbatim here. The
examples are the shapes the end-to-end suites
(`Tests/AeolusHelperTests/FanctlStatusTests.swift`, `FanctlAutoTests.swift`,
`FanctlSetTests.swift`) produce against the real helper session with a simulated fan authority. Replace them with captured output when someone
records a run.

### Every fan, and no target below the 50 % point (#670)

Until a hardware run shows that a fan left on automatic control beside a held one is still managed
(ADR 0014's U7, run 1d), the helper grants manual control of every fan together or of none. A lease
request that leaves out a fan the helper enumerated is refused `leaseMustCoverEveryFan`, exit 4
below, whose message says to ask for every fan at once; an `apply` must set every fan its lease
covers, or it is refused before anything is read. `fanctl set all` is the all-fans form, and
`fanctl set <n>` on a machine with more than one fan is that refusal.

Until run 2, the helper also holds no client target below a fan's 50 % point, the midpoint of
`[F<n>Mn, F<n>Mx]`: 3,563.5 RPM on `Mac16,5`. A lower request is held at the point, and the
helper's snapshot reports the target it holds, so `fanctl status` shows the raised value, and so
does `fanctl set`'s start line: `set all 20% --for 30m` says `Holding fan 0 at 3563.50 RPM target
(the helper's, not the 2235 RPM that 20% asked for; firmware 1350–5777 RPM)`, never "at 20%". Its
`--json` events already carried both, `commandedRPM` (sent) beside `observed.targetRPM` (held). The
app's 50 % preset is 3,564 RPM on that machine and passes unchanged. `status` and `auto` take no
lease and are unaffected; `auto` reads `leaseMustCoverEveryFan` as silent, since no snapshot
carries it.

### Exit codes

Stable, and a public contract: a script branches on the number without parsing text. A
number is never reused or renumbered; a new outcome gets a new number. Defined once, in
`FanctlExitCode` (`Sources/fanctl/FanctlExitCode.swift`), and `FanctlExitCodeTests` fails if
this table stops listing every code.

| Code | Kind | Meaning |
|---|---|---|
| 0 | `success` | Done, and what was reported was observed. |
| 1 | `failure` | Anything not named below: an answer this build cannot read, a request whose outcome is unknown because no answer arrived, an unanticipated error. |
| 2 | `requestDoesNotFit` | The request does not fit this machine: no such fan, a speed outside the fan's firmware range, a speed for a fan whose range is unusable (a percentage and an rpm alike). What is malformed on every machine is 64, not this. |
| 3 | `helperNotReachable` | Helper not installed, not approved, refused this binary's signature, or answered with a signature this binary refuses. These cannot be told apart from the client side. |
| 4 | `manualControlRefused` | The helper refused manual control of a fan it can see — the message carries the reason and its advice. |
| 5 | `heldByAnotherClient` | Another client holds the manual-control lease. There is one lease at a time. |
| 6 | `controlLost` | Control was held and then lost: renewal refused or unanswered, the lease could no longer be shown to be held (including while the speed was still being applied, and in the snapshot after it), the system reclaimed a fan, the helper stopped stating a held target for a fan, or a thermal emergency took over. |
| 7 | `protocolVersionMismatch` | This `fanctl` and the helper share no protocol version. The message names both. |
| 8 | `safeStateNotConfirmed` | A request for the safe state (releasing a lease, returning fans to automatic) that could not be confirmed. The lease still expires on its own. |
| 9 | `cannotReturnToAutomatic` | The helper reports `foreignManualControl` or `restoreToAutomaticFailed` for a fan, **whatever mode the fan reads** (an unreadable mode is reported as automatic). Durable: repeating the request will not change it. The message carries the reason and its `docs/RECOVERY.md` advice. *2026-10-10:* on a plane that can write, the request includes the machine-wide restore ([ADR 0014](ADR/0014-apple-silicon-unlock.md) D5), which can return a foreign-held fan to automatic; how a durable refusal is then reported is [#351](https://github.com/blamechris/Aeolus/issues/351). |
| 64 | `usage` | A malformed command line (swift-argument-parser's `EX_USAGE`). |

Which errors map where: every `HelperClientError` and `AeolusXPCFault` case is classified
exhaustively in `HelperCommandFailure`, with no default arm. The same refusal means different
things either side of holding a lease — `reclaimedBySystem` before one is 4, "you cannot have
this fan"; once a lease is held, **any** failure to keep it is 6, because the command can no
longer say it holds the fans.

`fanctl reset --all` predates this table and still exits 0 when the helper accepted the
request and 1 otherwise.

Under `--json`, a failure prints a machine-readable object on standard output as well as the
message on standard error, so a caller parsing stdout always gets JSON:

```json
{
  "failure" : {
    "exitCode" : 3,
    "kind" : "helperNotReachable",
    "message" : "The Aeolus helper did not answer. Either it is not installed or not yet approved, or it refused this copy of Aeolus because the signature did not match. These possibilities cannot be told apart from here."
  },
  "schema" : 1
}
```

### `fanctl status`

One `hello`, one `snapshot`, one disconnect. Reports, per fan, the actual speed, the firmware
range, the mode, the target, whether the system has reclaimed it and whether manual control is
available — with the reason and the advice for it when it is not (the same text
`docs/RECOVERY.md` step 4 lists). Separately from the fans: who holds the manual-control lease,
the helper's wall-clock estimate of its expiry, and whether it is self-renewing; whether a
thermal emergency is active; the protocol version negotiated with the helper; and the time the
helper captured the snapshot.

Everything is what the helper reported at that capture time. A **target** is what a lease
holder asked for, never a speed — the speed is `actual`. A lease that exists while a fan reads
`automatic` is two facts printed side by side, which is how a user sees that the holder is not
driving that fan.

Two things it deliberately does not infer:

- **No lease is not "nothing holds the fans".** It establishes only that no Aeolus client holds
  a manual-control lease. A fan beside it may be driven by another program, mid-handback, or in
  a restore nobody has confirmed; those are per-fan facts, on each fan's own lines.
- **The expiry is an estimate, and lease state is never derived from it.** `expiresAt` is the
  helper's wall-clock rendering of a deadline it enforces on monotonic time. A wall-clock step
  can put it before the capture time while the lease is active, so it is printed as an estimate
  and compared to nothing: a lease the snapshot lists is held.

```
$ fanctl status
Helper 0.0.0-dev, negotiated XPC protocol 2 (helper accepts 1–2; fanctl 0.0.0-dev speaks 2).
Captured by the helper at 2026-09-21T14:13:20Z.

Manual-control lease: none. No Aeolus client holds a manual-control lease.
Thermal emergency: not active.

Fan 0
  actual 1351 RPM · range 1350 RPM to 5777 RPM
  mode automatic · target none
  manual control: unavailable — This build of Aeolus has no path to write to the SMC yet, so manual control is not available for any fan. This is the expected answer for every fan on the current build; there is no user action that changes it yet. (reason: writePathNotBuilt)
```

### `fanctl status --json`

One pretty-printed document (below, each `RPM` reading object is collapsed onto one line to
save space; the real output breaks it across lines like every other object). `schema` is the
version of every helper command's `--json` shape: adding a field does not bump it; renaming, removing or re-typing one does. Every key is
always present, with `null` for "not present".

```json
{
  "capturedAt" : "2026-09-21T14:13:20Z",
  "clientProtocolVersion" : 2,
  "fans" : [
    {
      "actualRPM" : { "unavailableReason" : null, "value" : 1351 },
      "firmwareName" : null,
      "index" : 0,
      "isReclaimedBySystem" : false,
      "manualControl" : {
        "advice" : "This is the expected answer for every fan on the current build; there is no user action that changes it yet.",
        "reason" : "writePathNotBuilt",
        "state" : "unavailable",
        "summary" : "This build of Aeolus has no path to write to the SMC yet, so manual control is not available for any fan."
      },
      "maximumRPM" : { "unavailableReason" : null, "value" : 5777 },
      "minimumRPM" : { "unavailableReason" : null, "value" : 1350 },
      "mode" : "automatic",
      "targetRPM" : null
    }
  ],
  "helper" : {
    "build" : "0.0.0-dev",
    "capabilities" : [ ],
    "maximumProtocolVersion" : 2,
    "minimumProtocolVersion" : 1
  },
  "lease" : null,
  "protocolVersion" : 2,
  "schema" : 1,
  "thermalEmergencyActive" : false
}
```

- **`protocolVersion`** — the version the snapshot was encoded in; **`clientProtocolVersion`**
  the one this `fanctl` speaks; **`helper`** the handshake's answer (`null` if the connection
  was replaced before it could be read).
- **`lease`** — `null`, or `{ "id", "holderDescription", "expiresAt", "timeToLive",
  "isSelfRenewing" }`. There is at most one lease at a time, and the snapshot does not say
  which fans it covers. `expiresAt` is the helper's display-only wall-clock estimate; do not
  compare it to `capturedAt` or a local clock to decide whether the lease is active — a lease
  in the document is active. `null` means no Aeolus client holds a lease, not that no fan is
  under manual control; read each fan's `mode`.
- **`fans[].actualRPM` / `minimumRPM` / `maximumRPM`** — `{ "value": Double?,
  "unavailableReason": String? }`, exactly one non-null. A failed read is never a `0`.
- **`fans[].mode`** — `automatic`, `manualFixed` or `manualCurve`. **`targetRPM`** is the
  commanded target or `null`. `automatic` is also what a mode the helper could not read reports
  (#178), so read `manualControl` beside it: on a helper that can write, `supervisorBlind` there
  means the helper could not confirm the fan's mode. On today's builds `writePathNotBuilt` hides
  it (#178).
- **`fans[].manualControl`** — `state` is `available` or `unavailable`; when unavailable,
  `reason` is the stable wire value to branch on (`writePathNotBuilt`,
  `leaseHeldByAnotherClient`, `foreignManualControl`, …) and `summary`/`advice` are the text
  `docs/RECOVERY.md` step 4 lists.

### `fanctl auto`

Asks the helper to return every fan to automatic control, then checks what the helper reports.
`fanctl auto all` is the same command, and **`fanctl auto <index>` exits 64**: no request the
helper accepts returns one fan on behalf of another process, so an index would either do
nothing or quietly return other fans too.

```
handshake → snapshot
  no lease and every fan reads automatic → exit 0, nothing sent
  otherwise → one restoreAllToAutomatic, never re-sent in a run,
              then a snapshot every second for up to 10 seconds
              until it reports no lease and every fan automatic
```

- **It never takes a lease.** Not to return a fan, not briefly. A per-fan "acquire, apply
  automatic, release" reaches only fans that are already automatic, and the release then writes a
  restore to every fan the lease covered.
- **It may end another Aeolus client's lease, and says whose.** Commands that move toward the
  safe state may override another client; commands that move away from it may not (`set` gets 5).
  The client whose lease the request drops sees its lease lost (`6`), which is accurate. A lease
  listed before the request that is no longer listed afterwards is named in the text and in
  `--json`'s `endedLease`, as *no longer listed*: it may also have expired inside the window.
- **A fan the helper will not return is reported and `auto` exits 9.** It is never touched beyond
  the single request; what that request reaches is the helper's decision, and `auto` inherits it.
- **Exit 0 means the helper reports it, not that the fans are.** The helper reports a fan whose
  mode it could not read as automatic as well
  ([#178](https://github.com/blamechris/Aeolus/issues/178)), and on Intel every fan, so `auto`
  reads each fan's availability beside its mode, whatever the mode says (below). Every sentence it
  prints names the helper as its source and the time it captured the snapshot.
- **If the first snapshot fails *with the handshake still held*, the one request is sent
  anyway**, then the snapshot is read again; if it still cannot be, the exit is 8 and the message
  names `fanctl reset --all`, which needs no snapshot. **A first snapshot that times out, or
  whose helper restarts under it (XPC 4097), drops the connection and the handshake with it, and
  sends nothing**: the exit is 1, the message opens "No restore request was sent." and tells you
  to run `fanctl reset --all`. A handshake that failed sends nothing either (exit 3, or 1 with
  the same message), except a version mismatch (7).

A fan is **cleared** when its mode reads automatic and its availability does not say otherwise:

| Availability reason | What `auto` makes of it |
|---|---|
| `foreignManualControl`, `restoreToAutomaticFailed` | **9**, whatever the mode reads |
| `releaseInProgress`, `handbackUnconfirmed`, `restoreToAutomaticUnconfirmed`, `supervisorBlind`, `systemSleeping`, an unrecognised reason | **8**, whatever the mode reads: the helper has not established the fan's mode, or a restore is outstanding. `supervisorBlind` is unknown, not manual, so it is not 9 |
| `writePathNotBuilt`, `boundsImplausible`, `leaseHeldByAnotherClient`, `selfRenewalNotBuilt`, `leaseMustCoverEveryFan`, `noThermalTelemetry`, `reclaimedBySystem`, or none | The mode decides. `writePathNotBuilt` is every fan on today's helper, and `auto` against it exits 0 when all modes read automatic and no lease is listed |

A first snapshot with a fan the helper has not cleared is not the safe state, so the one request
is sent: it carries the `restoreAbandoned` sweep, which is such a fan's only route out.

| Code | When, for `auto` |
|---|---|
| 0 | The helper reports every fan automatic and no lease: on the first snapshot (nothing is sent), or within the window after the one request. |
| 9 | The helper reports `foreignManualControl` or `restoreToAutomaticFailed` for a fan when the window ends, whatever mode the fan reads. |
| 5 | A lease is listed when the window ends: someone took the fans after the request, or the request did not end it. The request is not repeated. |
| 8 | Not confirmed in the window (a manual fan, or a pending reason), the helper stopped answering after the request, or no snapshot could be read after a handshake. The message says which. |
| 3 | Helper unreachable. Nothing is sent. |
| 7 | Version mismatch. The one request is still sent — the helper exempts it from the version check — and the message says the result cannot be verified across versions. |
| 64 | `auto <index>`, or any argument but `all`. |

When several apply, **9 outranks 5 outranks 8**. 9 is judged at the end of the window, not on
the first sight of a reason: a fan mid-handback can be reported with a transient reason that
clears.

```
$ fanctl auto
The manual-control lease held by "Aeolus.app 0.3.0" (id 86663E1A-8A70-43D6-9B58-0DB87446531F) was listed before the restore request and is no longer listed. The request may have dropped it, or it may have expired; either way that client will find its lease gone.
Asked the helper once to return every fan to automatic control; it accepted the request.
The helper now reports every fan automatic and no manual-control lease, in a snapshot it captured at 2026-10-07T20:08:09Z.

Fan 0
  actual 1350 RPM · range 1350 RPM to 5777 RPM
  mode automatic · target none
  manual control: available
```

Already automatic, it says so and sends nothing:

```
$ fanctl auto
The helper reports every fan automatic and no manual-control lease, in a snapshot it captured at 2026-10-07T20:08:09Z. No restore request was sent.
```

A fan another program holds (exit 9; the result is on standard output, the diagnosis on standard
error):

```
$ fanctl auto; echo $?
...
The helper reports a reason for these fans that repeating the request will not change, and the mode a fan reads does not clear it:
  Fan 1 (reads manual): Something other than Aeolus has put this fan under manual control. Quit or stop the other program that is driving this fan. (reason: foreignManualControl)

This run sent the request once and will not send it again. What to do about each reason is in docs/RECOVERY.md, under "A specific fan says manual control is not available".

```

For `restoreToAutomaticFailed` the message adds that the advice naming `fanctl reset --all` is the
request this run already made, and the step that needs neither this command nor the helper
(stopping it). For a fan another program holds it does not, because stopping the helper does not
release it.

*2026-10-10:* on a plane that can write, the request includes the machine-wide restore

automatic; how a durable refusal is then reported is

### `fanctl auto --json`

One pretty-printed document, whatever the exit code, as long as a snapshot was read. `schema` is
the same version as `status`'s. Every key is always present, with `null` for "not present". `lease`
and `fans` are from the last snapshot the helper returned, captured at `capturedAt`; `lease`, `endedLease`, `fans[]` and
`failure` reuse the shapes `status --json` defines above and the failure object shown under
[Exit codes](#exit-codes).

```json
{
  "endedLease" : {
    "expiresAt" : "2026-10-07T20:08:39Z",
    "holderDescription" : "Aeolus.app 0.3.0",
    "id" : "BE1F82C3-F2C2-4033-8388-9589597802C7",
    "isSelfRenewing" : false,
    "timeToLive" : 30
  },
  "capturedAt" : "2026-10-07T20:08:09Z",
  "failure" : null,
  "fans" : [ ... ],
  "lease" : null,
  "restoreRequested" : true,
  "schema" : 1,
  "snapshotFollowsRestore" : true
}
```

- **`capturedAt`** — when the helper captured the snapshot `lease` and `fans` came from, as in
  `status --json`.
- **`restoreRequested`** — whether this run sent the request. `false` only when the first
  snapshot already reported the safe state.
- **`snapshotFollowsRestore`** — whether that snapshot was read **after the request was sent**, so
  `lease` and `fans` describe the helper after it. `false` when no request was sent, and when the
  wait could not read another snapshot and `lease` and `fans` are the ones from before the
  request. A script reads this instead of parsing `failure.message`.
- **`endedLease`** — the lease listed before the restore that is no longer listed after it, or
  `null`. It does not say the request dropped it: the lease may also have expired. A lease the
  request left standing appears in `lease` instead.
- **`failure`** — `null` on exit 0; otherwise `{ "exitCode", "kind", "message" }`, the `message`
  being the text written to standard error.
- A non-zero exit after a snapshot still carries `fans`. A run that could read no snapshot
  (exit 3, or 1, or 7 after the request was sent, or 8 after the request was sent on a
  handshake alone) prints the plain `{ "schema", "failure" }` document shown above instead,
  which has no `fans` and no `restoreRequested`; the failure message says whether the request was
  sent.

### `fanctl set <fan|all> <N%|Nrpm> --for <duration>`

A bounded hold for the life of the process. It takes the manual-control lease, sets the speed,
renews the lease every ten seconds from the moment it asks for it, and releases it when the time
is up, a signal arrives or its parent exits, and then checks what the helper reports the way
`auto` does.

> **Held.** `set` is built and tested against a simulated helper. It does not reach `main`
> before the safety subsystem (E5, [#7](https://github.com/blamechris/Aeolus/issues/7)) and the
> owner-supervised E4 acceptance ([#9](https://github.com/blamechris/Aeolus/issues/9)), per
> [#15](https://github.com/blamechris/Aeolus/issues/15). Nothing here has driven a fan. **Against
> `main`'s helper, `set` exits 4:** it answers every lease with `writePathNotBuilt`, and nothing is
> written. **Against a helper built with the write plane, `set` writes the fan.** The E4 branch's
> daemon holds a write channel on macOS 14 or later
> ([#465](https://github.com/blamechris/Aeolus/pull/465)), its plane answers `.built`, and `set`
> takes the lease, commands the speed and holds it. Below macOS 14 that helper answers
> `writePathNotBuilt` as `main`'s does. The Intel and M1/M2 paths are `untested`.

```
fanctl set 0 75% --for 30m            # fan 0 at 75% of its range for 30 minutes
fanctl set all 3000rpm --for 2h       # every fan at 3000 RPM; refuses if any fan cannot
fanctl set 1 100% --for 10s --json    # newline-delimited JSON events
```

Until run 1d, a helper that enumerates more than one fan refuses the one-fan forms
(`leaseMustCoverEveryFan`, exit 4), and until run 2 it holds a speed below a fan's 50 % point at
the point, so `3000rpm` is held at 3563.5 on `Mac16,5`: see
[Every fan, and no target below the 50 % point](#every-fan-and-no-target-below-the-50--point-670).

**The grammar.** Anything malformed is a usage error, **64**, before any connection. What is
well formed and does not fit this machine is **2**.

| Input | Accepted | Refused with 64 |
|---|---|---|
| fan | `all`, or a non-negative integer (`0`, `1`) | `ALL`, `-1`, `1.5`, `fan0`, `0,1` |
| speed | `<int>%` from 0 to 100, or `<int>rpm` (suffix in any case: `1350rpm`, `1350RPM`) | a bare number (`75`), `101%`, a sign, a decimal point, an exponent, a space, `nan%`, `inf%`, a digit from another script, a number too large for an integer |
| `--for` | `<int>s`, `<int>m` or `<int>h`, from `10s` to `8h` | no `--for` at all, `9s`, `9h`, `30` (no unit), `1h30m`, `30M` |

ASCII digits only, so `nan`, `inf`, `+5` and `٣٠` cannot be a speed or a duration. There is **no
`--persist` flag**, and nothing like one: the flag is absent, not refused. `--for` is required on
every `set`, because a terminal cannot be told from an automated caller (chroxy, `ssh -t`, tmux
and expect all allocate a PTY). A hold at a terminal is `--for 2h`, and Ctrl-C still ends it
early. The bounds are one heartbeat at the bottom (a shorter hold only churns the fan's mode
register) and eight hours at the top (a longer one is persistence, which ADR 0007 refuses in v1).

**What a percentage means.** A position in the **commandable** range, not in `[0, max]`:
`rpm = lowest + p/100 × (highest − lowest)`, rounded to a whole RPM, where `lowest` is
`max(F0Mn, 100)` (the floor that keeps a fan off zero, `FanSafetyLimits.minimumManualRPM`) and
`highest` is `F0Mx`. On `Mac16,5` (1350 to 5777 RPM): 0% is 1350, 50% is 3564, 75% is 4670,
100% is 5777. The mapping is `FanControlEnvelope.target(forPercent:)` in `FanKit`, once, so the
app's slider and a remote caller cannot round it differently. On Intel and M1/M2 the mapping
rests on the documented `F0Mn`/`F0Mx` only.

**The gate, and what is refused (exit 2).** Everything is decided from the helper's own snapshot
before anything is acquired:

- A fan whose `FanState.controlEnvelope` is not `.success` gets **no speed in either unit**: a
  bound that was not read, or one `FanBoundsImplausibility` refuses (a declared maximum of 1e14
  would make 75% about 7.5e13 RPM, and the helper would grant the lease anyway,
  [#270](https://github.com/blamechris/Aeolus/issues/270)). The message is
  `FanBoundsImplausibility`'s own description.
- An rpm outside `[lowest, highest]` — `0rpm` included — is refused, **never clamped** on the
  client. The helper still clamps (CLAUDE.md rule 7); that is its control, not this command's
  courtesy.
- A fan the helper does not report.
- `all` is **all or nothing**: each fan is judged against its own envelope, and one that cannot
  be set refuses the whole command with nothing acquired.

```
handshake → snapshot → validate (2) → [clock read] → acquireLease (30 s, not self-renewing,
  held by "fanctl <version> (pid N)") → apply, with renewLease every 10 s from the clock read
  until apply is answered → a snapshot in which every covered fan carries the helper's held
  target → started
  every 10 s, on the same schedule: renewLease, then snapshot → holding
  ends: --for elapsed │ SIGINT/SIGTERM/SIGHUP │ the parent exited │ stdout not draining
  then: releaseLease → the safe-state check (the one `auto` ends on) → ended
  or, on any loss the helper reports once holding: releaseLease → the safe-state check → failed,
  exit 6 or worse
  or, on any outcome before started (apply refused, or no answer, or control no longer shown
  held, a snapshot that failed or showed no hold): releaseLease → the safe-state check → failed
```

- **The lease is renewed from the moment it is asked for.** The helper's thirty seconds start at
  the grant, and an `apply` may take 57 seconds for one fan and 109 for two. The first renewal is
  due ten seconds after the instant read **before `acquireLease` is sent**, and renewals are sent
  while `apply` and the confirming snapshot are outstanding. When they are answered the hold's
  loop takes the same schedule over: there is one, and no renewal is sent after the release.
  A renewal that fails is final (it is never retried), and is reported once `apply` has been
  answered, and **it takes precedence**: whatever `apply` then said, the diagnosis is control
  lost and the text states both facts. (A renewal that times out makes the client give up the
  connection, and the `apply` in flight is then answered `connectionAbandoned`; read alone, that
  would be "no answer" and the renewal would never be mentioned.)
- **Control starts when `apply` is accepted and the helper shows the fans held.** "Holding" is
  said when the snapshot after `apply` lists this lease **and** every covered fan carries the
  helper's held target (`observed.targetRPM`, `null` unless the same snapshot shows the fan in
  manual under the live lease, with no reclamation and no thermal override). That snapshot is
  read after `apply` was answered and cannot predate the engagement (ADR 0013, 2026-10-18), so
  the first one decides.
- **Control that could no longer be shown to be held is control lost before the hold began,
  never a refusal.** A renewal failed while `apply` worked; `apply` answered `leaseExpired`,
  `leaseUnknown` or `leaseNotHeldByThisConnection`; or `apply` was accepted and the snapshot
  after it could not be read, did not show every covered fan with the helper's held target, or
  the keeper's timer failed. The message opens "Control was lost before the hold began: control
  of lease … could no longer be shown to be held", states what was seen, in order, and never
  says the helper refused or did not accept the speed, and never that the lease **ended**:
  nobody saw an end. `endedBecause` is `controlLost`. The lease is released and the safe-state
  check **looks**: the exit is 6, or 9 or 8 if the check found something worse, and the closing
  text states that check's verdict and says "nothing is held" only if the check confirmed it.
  The text does not repeat the helper's or the client's own descriptions of `leaseExpired`, a
  restarted helper, or a connection given up, which claim what became of the fans ("have
  returned to automatic control") or advise asking again; nothing observed that, so the text says
  what was seen ("The helper answered that the manual-control lease had expired.").
- **A signal that lands while `apply` is outstanding** is remembered and cannot cut `apply`
  short (that would release the lease under an `apply` that is working); it takes effect when
  `apply` returns, bounded by `apply`'s own deadline (57 s for one fan, 109 s for two). It ends
  the run **before `started`**, so "Holding" is never printed to a person who has already asked
  to stop: released, checked, an ordinary ending with `endedBecause: signal` and exit 0, 8 or 9,
  whose text opens "The hold was not begun", not "The hold ended". The signal is looked for once
  `apply` and the snapshot confirming it are both answered, so it may have landed during either,
  and the text says "while the speed was being applied or confirmed". If the run ends some other
  way, the signal is still in the closing event (`signal`) and in the text.
- **An `apply` the helper answered with a fault is followed by a release and the safe-state
  check, whatever the fault.** Level 6 can engage a fan, fail on the next, have the undo refused
  and answer only the original fault, so a refusal is not taken to mean no fan was touched. The
  exit is the check's verdict where that is worse (9, then 8) and otherwise the code the fault
  classifies to (4 for a bounds refusal or a thermal emergency, 2 for an invalid parameter, …).
  "Did not accept the speed" is said, and `endedBecause` is `refused`, **only if the check found
  every fan automatic and no lease**; otherwise the text says the answer does not settle what
  happened to the fans, and `endedBecause` is `controlLost`.
- **An `apply` that got no answer is not a refusal.** The helper may have applied the speed, so
  the message says it got no answer and may have been applied, never "did not accept". The lease
  is released (best effort), the safe-state check **looks**, and the exit follows the same rule
  as a fault's: the check's verdict where that is worse (9, then 8), and otherwise the code the
  failure classifies to (1 for a restart, a lost reply, an abandoned connection or no answer
  within the deadline; non-zero always). It is reported as `endedBecause: controlLost`, with the
  check's verdict in the message and `snapshotFollowsRelease` in the closing event.
- **A signal that lands while `acquireLease` is in flight** stops the speed being sent: after the
  lease comes back and before `apply`, a pending signal releases the lease, sends nothing to a
  fan, and ends with exit 1, `endedBecause: signal`.
- **The deadline is on the monotonic clock**, never compared with `Lease.expiresAt`, which is
  the helper's display estimate. A step in the wall clock cannot lengthen or shorten a hold, and
  no event carries a wall-clock end time.
- **Ending.** A signal ends the sleep and nothing else: the release that follows is not
  cancelled, and a signal during the release or the check is ignored. `getppid()` is compared with
  its starting value at every heartbeat. Then the lease is released and the safe-state check
  runs: 0, 8 or 9, exactly as for `auto`. A standard output that is not draining ends the hold
  too (see **A write may park; the hold never waits on it**, below).
- **Exit 6 on any loss the helper reports**, after a release **and the safe-state check** (exit 8 or
  9 instead if the check found them, and "nothing is held" is never said on the release's word: only
  the check's own sentence confirms the fans, and during a thermal emergency the text says the
  helper reports its thermal protection, not `set`, in control of them): a renewal that errored
  (whatever the error), a snapshot that does not list this run's lease, `isReclaimedBySystem` on a
  fan the lease covers, `thermalEmergencyActive`, or **a covered fan the snapshot states no held
  target for**. It never retries and **never re-acquires**: a helper that restarts mid-hold sends
  exactly one `acquireLease` and ends in 6. A covered fan the snapshot no longer reports at all is a
  loss too (not in the contract's list; the safe direction). The held target is the evidence that a
  fan is held, at the confirming snapshot and at every heartbeat: a fan the firmware took back
  before the reclamation watchdog marked it reads `automatic` with no target beside a lease the
  helper still lists, and that ends the hold. **The mode alone is not a loss either way**: the
  helper reports an unread mode as automatic
  ([#178](https://github.com/blamechris/Aeolus/issues/178)), so a fan that reads `automatic` beside
  a lease the helper lists and a held target is still held, and one that reads manual with no target
  is not.
- **SIGKILL and SIGSTOP** are beyond any of this: the 30-second lease expires on its own, a
  stopped process finds its lease gone on resume and ends in 6, and sleep drops the lease (SAFETY.md
  § 4). Whether the system reclaims a fan routinely and briefly on M3 and newer is **unobserved**;
  if it does, holds end early, which is the safe direction.
- **An orphan whose shell survives** (under tmux, say) is bounded only by `--for`, at most 8 hours.

| Code | When, for `set` |
|---|---|
| 0 | The hold ended in an ordinary way and the helper reports every fan automatic and no lease after the release. |
| 2 | The request does not fit this machine (above), decided from the first snapshot: nothing was acquired. (An `apply` answered with `invalidParameter` is also 2, after the lease was taken, released and checked, unless the check found something worse.) |
| 3 | The helper cannot be reached. Nothing was acquired, except when an `apply` got no answer and the failure is `clientCannotVerifyHelper`, `helperUnreachable` or `helperSignatureRejected`: the lease was taken, and is released and checked. The exit is 3 only if the check then finds the safe state; it usually cannot read, and the exit is 8. |
| 7 | Version mismatch. Nothing was acquired. |
| 4, 5 | The helper refused the lease: manual control unavailable (`writePathNotBuilt`, from `main`'s helper, or from a helper built with the write plane below macOS 14), or another client holds it. Nothing was acquired or applied. (An `apply` answered with `boundsImplausible`, `thermalEmergencyActive`, `reclaimedBySystem` or `manualControlUnavailable` is also 4, or 5 for `leaseHeldByAnotherClient`, after the lease was taken, released and checked, unless the check found something worse.) |
| 6 | Control was held and lost: a renewal failed, the helper does not list the lease, states no held target for a covered fan, reclaimed one, or set a thermal emergency. Released and checked, and 8 or 9 instead if the check found them: during the hold, or **before `started`**: a renewal that failed while `apply` was outstanding (whatever `apply` then said, including no answer), `apply` answering `leaseExpired`, `leaseUnknown` or `leaseNotHeldByThisConnection`, a snapshot after an accepted `apply` that could not be read or did not show every covered fan held, or the renewing timer failing. |
| 8 | After the release the helper did not report the safe state within 10 seconds (a fan still manual, a lease still listed — this run's, or another client's, which the message says — or the helper stopped answering). Also the exit for a loss, an `apply` fault, an `apply` that got no answer, or a lapse, followed by that. |
| 9 | The helper reports `foreignManualControl` or `restoreToAutomaticFailed` for a fan, whatever mode it reads. Also the exit for a loss, an `apply` fault, an `apply` that got no answer, or a lapse, that left a fan so. |
| 1 | The first snapshot could not be read, or `acquireLease` failed in a way no other code names (nothing acquired); a signal arrived before control was taken, or while the lease was in flight (nothing was written to a fan); an `apply` got no answer (released and checked; the exit is the failure's own code, 1 for a restart, a lost reply, an abandoned connection or no answer within the deadline, and 8 or 9 instead if the check found them; but 6 if a renewal had failed while it was outstanding), or was answered with a fault no other code names (`helperFailed`, `malformedPayload`, `handshakeRequired`, one this build does not recognise; released and checked, and 8 or 9 instead if the check found them); or the hold's own timer failed once the hold is under way (released and checked, and 8 or 9 instead if the check found them; before `started` it is 6, above). |
| 64 | Malformed command line (above). |

**Text.** At the start, one line per fan and the lease, naming the target the helper holds (the

### `fanctl set --json`

Newline-delimited JSON: one compact object per line, in this order and no other. Every line has
`schema` (the same version as `status`'s), `event` and `at` (the time the line was written). Every
key a shape defines is always present, `null` for "not present".

| Event | When |
|---|---|
| `started` | Once, after `apply` was accepted and a snapshot listed the lease with the helper's held target for every covered fan (`observed.targetRPM` is not `null`). Never implies a fan reached its speed. |
| `holding` | After every successful heartbeat: the liveness signal, and the line a consumer that is not draining is found out by. |
| `ended` | Exactly one closing event for exit 0, on standard output or, when that cannot take it whole, standard error. |
| `failed` | Exactly one closing event for every other exit — including one that never held anything — on the same terms. |

```json
{"at":"2026-10-07T23:24:57Z","durationSeconds":20,"event":"started","fans":[{"commandedRPM":4670,"index":0,"observed":{"actualRPM":{"unavailableReason":null,"value":1350},"firmwareName":null,"index":0,"isReclaimedBySystem":false,"manualControl":{"advice":null,"reason":null,"state":"available","summary":null},"maximumRPM":{"unavailableReason":null,"value":5777},"minimumRPM":{"unavailableReason":null,"value":1350},"mode":"manualFixed","targetRPM":4670},"requested":{"unit":"percent","value":75}}],"leaseID":"FEDA5A4F-912F-49CB-84B7-51288910401A","schema":1}
{"at":"2026-10-07T23:24:57Z","event":"holding","fans":[ ... ],"leaseID":"FEDA5A4F-912F-49CB-84B7-51288910401A","remainingSeconds":10,"schema":1}
{"at":"2026-10-07T23:24:57Z","capturedAt":"2026-10-07T23:24:57Z","endedBecause":"durationElapsed","event":"ended","failure":null,"fans":[ ... ],"leaseID":"FEDA5A4F-912F-49CB-84B7-51288910401A","listedLeaseID":null,"releaseAccepted":true,"schema":1,"signal":null,"snapshotFollowsRelease":true}
```

- **`started` and `holding`** — `leaseID`; `fans[]`, one per fan the hold covers, each
  `{ index, requested: { unit: "percent" | "rpm", value }, commandedRPM, observed }`. `requested`
  is what was typed; **`commandedRPM` is the target that was sent**; `observed` is the helper's own
  report of the fan at that snapshot, in the shape `status --json` defines for `fans[]` (`actualRPM`
  is the speed, `targetRPM` the helper's target, `mode`, `isReclaimedBySystem`, `manualControl`).
  `started` adds `durationSeconds` (what was asked for); `holding` adds `remainingSeconds`, whole
  seconds counting down. **No event carries a wall-clock end time.**
- **The closing event** — `ended` and `failed` share these, and `failed` is the existing failure
  event (`schema`, `event`, `at`, `failure: { exitCode, kind, message }`) extended additively; the
  shared keys are `null` wherever there is nothing to say.
  - `leaseID` — the lease this run took, or `null` if it never took one.
  - `endedBecause` — `durationElapsed`, `signal`, `parentExited`, `outputClosed`, `controlLost` or
    `refused`; `null` when fanctl never tried to take control (3, 7, 1 before any lease), and when
    the hold's own timer failed (1, or 8 or 9 where the check found worse), which is neither an
    ending anyone asked for nor a loss the helper reported.
    `refused` is a "no" to the request: exit 2, 4 or 5 before a hold, or an `apply` the helper
    answered with a fault **and the safe-state check that followed found every fan automatic and
    no lease**. An `apply` fault followed by anything else, an `apply` that got no answer, and
    control that could no longer be shown to be held before the hold began (a renewal that failed
    while `apply` worked, an `apply` answered that the lease was gone, a confirming snapshot that
    failed or showed no hold, a keeper that could not pace itself) are `controlLost`: nobody saw
    the lease end. A signal is `signal` when it arrived before the lease, while the lease was in
    flight, or while `apply` and its confirming snapshot were outstanding and they then showed the
    fans held: the last is an ordinary ending before `started` (0, 8 or 9), whose text says the
    hold was not begun.
  - `signal` — `SIGINT`, `SIGTERM` or `SIGHUP`, whenever `endedBecause` is `signal`, and also when
    a signal landed while `apply` was outstanding and the run then ended some other way.
  - `releaseAccepted` — whether the helper accepted the request to release the lease; `null` if
    none was made. `false` is not "the lease is still there", only that no acceptance was heard.
  - `capturedAt`, `snapshotFollowsRelease`, `listedLeaseID`, `fans` — the last snapshot the helper
    returned: when it was captured, whether it was read after the release, the lease it listed
    (whoever holds it), and the covered fans as in `started`. After an ordinary ending these are
    the safe-state check's, so `fans[].observed.mode` is what the helper reports after the release.
    **`snapshotFollowsRelease: false` means they describe the helper while the lease was still
    held**, because the check read nothing afterwards; the text then says the state is unknown
    and does not describe the lease or the fans at all.
  - `failure` — `null` for `ended`.

**A write may park; the hold never waits on it.** A process that holds a lease must keep
renewing it and must be able to stop, and a `write(2)` to a pipe can park for as long as the
kernel makes it: a reader that stopped reading, a terminal under flow control (Ctrl-S), another
process racing for the room on a shared pipe, a system at its pipe-memory ceiling. Nothing that
can be checked before a write promises it will not park (`poll` calls a pipe writable at
`PIPE_BUF` bytes free, which a `--json` line of 560 to 1,127 bytes is longer than; calls a full
pipe writable at the memory ceiling; and says nothing of a terminal under XOFF), so `set` does
not write. It hands each line to a **writer thread of its own**, one per stream, which may park in
`write(2)` for as long as the kernel makes it. Handing a line over never blocks, and nothing the
hold does waits on a write. Four consequences:

- **A consumer that is not draining is judged by the writer's progress, not by `poll`.** If the
  oldest line handed to standard output is not completely written 2 seconds after it was handed
  over, or the write failed (the reader is gone), the hold releases and ends with
  `endedBecause: outputClosed`, well inside the 10-second heartbeat. A stop request (a signal, the
  parent exiting, `--for` elapsing) never waits on the writer, and is the reason the hold ends
  whenever there is one.
- **Output cannot delay the release or the check.** The lease is released and the safe state
  checked first; only then is the closing event handed over.
- **The closing event reaches exactly one stream, whole.** If standard output is idle within one
  second of the ending (every line handed to it has been written, so it is at a line boundary),
  the event is its last line. Otherwise (a line is parked on it, perhaps half-written; or it has
  failed) the **same line** is written to standard error, and a diagnosis in words for a failed
  ending is always on standard error. If standard error does not take it within one second
  either, it is dropped and the process exits; the exit code still tells. A script should take
  the closing event from standard output or, failing that, standard error.
- **Process exit abandons a parked writer thread.** The bytes it had already written stay in the
  pipe, so standard output can end with the front of a line it was parked on and no newline: an
  incomplete final line, never a complete one that does not parse, and never one with the closing
  event glued to it. In text, the closing sentence follows the same rule.

**`status` and `auto` write to the end.** Their output is delivered whole to a reader that is
merely slow, however little room the pipe has; a reader that has *gone* (EPIPE) neither crashes
the command nor changes its exit code. Any other write failure (a closed descriptor, a full disk)
is said on standard error and also leaves the exit code alone. On an inherited **non-blocking**
descriptor (a child of a Node process, whose pipes are), a full pipe is `EAGAIN` and not a wait:
the write waits for room with `poll` and retries, and never changes the flag, which belongs to
the open file description every process sharing the descriptor shares. `reset --all` does not use
this writer.
